## 3. Структура файлов

```
G:\SlavaSaitOffer\site\
├─ PROJECT.md         ← этот файл — ВСЁ для быстрого входа (отдай другой ИИ)
├─ config.json        ← ВСЕ данные сайта (бренд, телефон, город, районы, бренды)
├─ build.py           ← сборщик: читает config.json, собирает папку docs/
├─ admin_src.html     ← шаблон админ-панели (пока заглушка)
├─ apps_script.gs     ← код бэкенда (НЕ используется, оставлен на будущее)
├─ policy.py          ← генерит politika.html, soglasie.html, requisites.html
├─ seo.py             ← генерит robots.txt, sitemap.xml, 404.html
├─ render_brand.py    ← генерит og-картинку и favicon (нужен Playwright)
├─ setup.py           ← мастер: задаёт вопросы и сам правит config.json
├─ deploy.sh          ← сборка + коммит + пуш на GitHub
├─ check.py           ← проверка битых ссылок
├─ src\               ← исходник-оригинал и ассеты (НЕ ТРОГАТЬ)
└─ docs\              ← ГОТОВЫЙ САЙТ. Именно он уходит на хостинг.
   ├─ index.html
   ├─ admin\index.html
   ├─ politika.html, soglasie.html, requisites.html
   ├─ 404.html, robots.txt, sitemap.xml
   └─ public\, content\, assets\
```

**Правило:** правим `config.json` → запускаем `build.py` → в `docs/` готовый сайт.
Никогда не правим файлы в `docs/` руками — они перезапишутся при следующей сборке.

## 4. Как собрать и задеплоить

```bash
cd G:/SlavaSaitOffer/site
python build.py        # пересобрать docs/
git push               # запушить на GitHub Pages (gh auth может протухнуть)
```

Сайт обновляется на `linar.me/holodok` через 1–2 минуты после пуша.

Проверка перед деплоем:
```bash
python check.py        # покажет битые ссылки (должно быть «БИТЫХ: 0»)
```

Если нужно изменить данные без правки JSON вручную:
```bash
python setup.py        # задаст вопросы и сам обновит config.json + соберёт
```

`deploy.sh` (сборка + коммит + пуш + `gh repo create` при необходимости) — может
падать на `gh repo create`/`gh repo view` если gh auth протух. В этом случае
обычный `git push` работает через кэшированный credential helper.

## 6. Заявки и веб-админка (как устроено СЕЙЧАС)

**Заявка уходит из браузера в хранилище Supabase:**

```
Гость → форма на сайте → POST {supabase}/rest/v1/leads
       (публичный anon-ключ; RLS разрешает только вставку)
          → таблица заявок
Гость видит «Спасибо, заявка отправлена»
```

- В браузере нет никаких секретов — только публичный anon-ключ.
- Пароли админок и служебные настройки хранятся на сервере Supabase
  (`private`-схема, извне недоступна), в коде сайта их нет.
- Смена пароля админки: `UPDATE private.admin_auth SET pw='новый' WHERE site='holodok';`
  (SQL-редактор Supabase).

**Веб-админка:**
- Заявки читаются из таблицы `leads` только через закрытую серверную функцию
  с проверкой пароля (rpc `admin_leads_site`)
- Админка лежит по неочевидному адресу `admin/` (основная защита)
- Вход по паролю — пароль проверяется **на сервере**, в HTML его нет
- **В админке НИ СЛОВА про каналы доставки** — только логотип, таблица заявок,
  фильтры, статистика, экспорт CSV, изменение статусов/комментариев
- Эта админка видит **только заявки этого сайта** — изоляция на стороне сервера

**Supabase уже подключён и проверен:**
- Project URL: `https://wedeflvoryfdkzuodgzg.supabase.co`
- Таблица `public.leads` создана, RLS включён
- RPC `admin_leads_site`: веб-админка не читает таблицу напрямую, а работает через
  закрытую серверную функцию с проверкой пароля; каждая админка видит только свой сайт
- В конфиге хранится только publishable/anon ключ; секретов на сайт не попадает

**Чтобы открыть панель:**
`https://www.tulyacenterorg.ru/admin/` → пароль у владельца (хранится на сервере
Supabase, `private.admin_auth`).

**Если нужен Apps Script вместо Supabase** (старая схема, оставлена на всякий случай):
файл `apps_script.gs` — Google Таблица + пересылка + JSON API. Работает, но требует
больше ручных шагов. Supabase проще.

домен сейчас делегирован на сторонние DNS-серверы. Поэтому добавлять A-записи надо
не в этой вкладке, а у DNS-провайдера, чьи NS указаны у домена. Если NS должны быть
SpaceWeb — в настройках делегации выбери DNS SpaceWeb, дождись активации, затем в
управлении DNS замени старые A-записи `77.222.40.65` на GitHub:

```
A     @      185.199.108.153
A     @      185.199.109.153
A     @      185.199.110.153
A     @      185.199.111.153
CNAME www    sweedoom.github.io
```

Старую A-запись `77.222.40.65` для `@` нужно удалить/заменить. Для `www` тоже убрать
старый A `77.222.40.65`, оставить CNAME. Не трогай MX, TXT, autoconfig и autodiscover
— они нужны для почты.

Сейчас внешняя проверка DNS отдаёт `NXDOMAIN`, то есть делегация ещё не опубликована.
Как только записи появятся, я проверю DNS, включу Enforce HTTPS в GitHub Pages и
подтвержу адрес `https://tulyacenterorg.ru/`.

## 8. Грабли (уже решено — не наступать снова)

1. **`shutil.rmtree` в `build.py`** на Windows валится через корзину →
   сборка НЕ удаляет `docs/`, а перезаписывает (`copytree(dirs_exist_ok=True)`).
2. **Папки с `_`** — GitHub Pages/Jekyll их игнорирует → `_content` → `content`.
3. **Плейсхолдеры подстановки** — `@LEADS_BACKEND@` и `__BACKEND__` разные!
   Если сделать их одинаковыми, `.replace()` подставит URL внутрь проверки и
   админка сломается.
4. **`is-hidden`** у брендов — после фильтрации нужно снимать, иначе сетка пустая.
5. **Классы с модификаторами** — regex должен быть `class="[^"]*\bИМЯ\b[^"]*"`,
   а не `class="ИМЯ"` (иначе `t74-brands__item is-hidden` не матчится).
6. **Переносы строк внутри тегов** — литеральный `.replace()` не работает,
   нужен regex с `[^<]*`.
7. **Их JS без null-проверок** — после удаления элементов (меню, кнопки)
   `$(...).offset()` падает. Проверять `pageerror` в Playwright.
8. **gh auth протухает** — тогда `bash deploy.sh` не пушнет, но обычный
   `git push` через кэшированный credential helper работает.
9. **GitHub Pages CDN (Fastly) кэширует редирект кастомного домена** — после
   удаления CNAME может 10–30 мин перенаправлять на старый домен. Подождать или
   push ещё раз.
10. **Секреты не хранятся в репозитории**: пароли и токены живут только на сервере
    Supabase (`private`-схема). В `config.json` и собранном HTML их нет.
